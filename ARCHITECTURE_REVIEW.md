# Architecture Review
Generated: 2026-10-08T18:04:43.172Z
Score: 68/100

## Summary
The codebase is a small, well-layered React/TDS mini-app with a clear separation between pure domain logic (lib/engine, lib/schema, lib/store), reusable UI primitives, and feature-scoped component folders. Structure is largely sound, but there are real issues: a circular dependency in the schema modules, many duplicated SDK-guard/formatting helpers, mixed quote/path-alias/export conventions, and a number of apparently unused template exports and files in lib/.

## Issues
### Warnings
- [circular_dep] Circular imports within the schema layer. src/lib/noticeSchema.ts re-exports from schema/validateNotices, schema/versioning and schema/corruptBackup, while schema/versioning.ts imports CURRENT_SCHEMA_VERSION and MIGRATIONS from noticeSchema, and schema/corruptBackup.ts imports MAX_CORRUPT_BACKUPS from noticeSchema. This is a direct cycle (noticeSchema -> versioning -> noticeSchema; noticeSchema -> corruptBackup -> noticeSchema). It only works because the constants are declared before the re-exports are evaluated, which is fragile under ESM reordering and easy to break. — Files: src/lib/noticeSchema.ts, src/lib/schema/versioning.ts, src/lib/schema/corruptBackup.ts / Fix: Move the constants (CURRENT_SCHEMA_VERSION, MAX_CORRUPT_BACKUPS, MIGRATIONS, NoticesData/CorruptBackup types) into a leaf module such as src/lib/schema/constants.ts. Have versioning.ts and corruptBackup.ts import from that leaf, and keep noticeSchema.ts as a pure barrel that only re-exports.
- [duplication] The 'fire haptic feedback inside try/catch with Promise.resolve().catch' snippet is copy-pasted in at least five places, even though BottomCTA.tsx already has a local fireHaptic and analytics/share/review each wrap SDK calls independently. — Files: src/components/BottomCTA.tsx, src/components/FloatingTabBar.tsx, src/components/form/NoticeFormFields.tsx, src/components/home/NoticeCard.tsx, src/components/result/useRecordActions.ts, src/pages/Home.tsx / Fix: Create a single src/lib/haptics.ts exporting fireHaptic(type: 'success' | 'tickWeak' | ...) and replace all local copies (fireTickWeak, tickWeak, fireHaptic, inline try/catch) with imports of it.
- [duplication] Business rules for computing the recorded amounts are implemented twice. engine/deadlines.ts has calcDecisionRecord (paid amount, saved amount, decidedAt per status) while store/mutateNotice.ts has its own recordFor with a different savedAmount formula (potentialSaving vs. worst-case difference). The two give different results for the same action (e.g. test expects 9200 saved in calcDecisionRecord, whereas updateStatus uses potentialSaving=8000). calcDecisionRecord appears unused by production code, so the divergence is a latent bug. — Files: src/lib/engine/deadlines.ts, src/lib/store/mutateNotice.ts / Fix: Pick one canonical implementation (calcDecisionRecord or recordFor), have mutateNotice call it, and delete the other. Reconcile the savedAmount semantics with the spec and add a test covering the store path.
- [consistency] State/data access patterns are inconsistent. Pages read through the useNotices hook (which wraps noticeStore and reloads), but DeleteNoticeButton, useNoticeSubmit and useRecordActions call noticeStore functions (deleteNotice, saveNotice, updateStatus) directly and bypass the hook, so reload is wired via callbacks in some places (RecordSheet.onRecorded) and not in others. useNotices also exposes save/remove/updateStatus that nothing uses, leaving two parallel mutation paths. — Files: src/lib/useNotices.ts, src/components/result/DeleteNoticeButton.tsx, src/components/form/useNoticeSubmit.ts, src/components/result/useRecordActions.ts, src/pages/NoticeResult.tsx / Fix: Choose a single path: either have components consume mutations from useNotices (or a NoticesContext shared by pages), or strip the mutators from useNotices and keep it read-only. Prefer a context/provider so result state is shared and reload after writes is automatic.
